# Klaro — Mini AI Analyst as a Service — Upgrade Plan

> Generated from a senior multi-disciplinary audit (product · AI/ML · backend · frontend · architecture). Roadmap to take this project to its expected full form. Tackle order across all 3 repos: **Klaro → ArcherReview → CryptAI**.

## Vision (full form)
Klaro is a "Mini AI Analyst as a Service": a logged-in user uploads a CSV and within one guided flow gets real statistical profiling (distributions, correlations, outliers, leakage detection), trains and evaluates an AutoML model, runs single and batch predictions with calibrated confidence, and reads an LLM-generated plain-English summary of their data and model. In full form every button works and every number shown is real and user-scoped, the AutoML actually does smart model selection plus hyperparameter tuning on a non-blocking background worker, the LLM layer is async/cached/grounded, and the whole thing ships as two hardened, env-configured Docker images (frontend on Vercel/container, FastAPI on a container platform with managed Postgres + object storage) behind CI that runs real tests, type checks, and lint. The repo is lean: one README plus a small docs/ set, no dead code, no committed secrets or PII.

## Current state
The core loop (upload → profile → train RF/LogReg/XGBoost via a leak-safe sklearn Pipeline → predict → LLM summary with template fallback) is genuinely implemented end-to-end and demoable on the happy path, with JWT+bcrypt auth, SQLite persistence, and a polished Next.js 15 glassmorphism UI. But it is a take-home dressed as enterprise software, and I verified the seams in the code: POST /predict/batch crashes (TypeError, calls make_predictions(request) without current_user at predict.py:185); the train UI offers SVM that POST /train/ rejects with 400; the homepage shows hardcoded fake "Recent Activity"/94.2% accuracy and the predict page hardcodes 0.95 accuracy; nav links to non-existent /docs, /predict/sample-model, and /auth/login (real route is /login). Security is broken: POST /predict/ and all /summary/* load models by id with NO ownership check (IDOR), GET /predict/models and GET /upload/session/{id}/info have no auth at all. The "AutoML/enhanced" layer is dead: /{session_id}/enhanced-train is declared twice (train.py:257 and :643) so the smart-selection handler is unreachable, the enhanced ml path references an undefined `preprocessor`, and the GridSearch/hyperparameter engine is never called by any endpoint. Infra is unsafe: database.py:31 uses raw conn.execute("SELECT 1") which throws under SQLAlchemy 2.0 (Postgres silently falls back to SQLite), main.py uses deprecated @app.on_event with hardcoded localhost CORS ignoring ALLOWED_ORIGINS, docker-compose hardcodes SECRET_KEY and POSTGRES_PASSWORD, NEXT_PUBLIC_API_URL is baked to localhost:8001 at build time, and a SQLite DB containing a real email + bcrypt hash is committed. Quality gates are off (next.config ignores TS+ESLint errors), the pytest suite is stale (pre-auth, will 401), there is no CI and no alembic config despite alembic being a dependency, and the repo carries dump/ (800K dead code), ~1,760 lines of unused viz components, ~8 unused deps, 9 markdown docs + a .docx + transcript.md, and 6 startup scripts.

## Runs today?
Yes on the happy path. `docker-compose up --build` boots both services (backend create_tables() runs at startup, SQLite default, LLM degrades to templates with no OPENROUTER_API_KEY) and the upload→profile→train→predict→summary flow works in the browser. Locally without Docker: backend `cd backend && pip install -r requirements.txt && uvicorn app.main:app --port 8001` (must be started from backend/ because several modules hardcode relative paths like data/models, data/uploads), frontend `cd frontend && npm install && npm run dev` (node_modules/.next not present, must install first). Caveats: the build "passes" only because TS+ESLint are suppressed; the pytest suite will fail (written pre-auth); Postgres is de facto broken (SELECT 1 throws under SQLAlchemy 2.0 and silently falls back to SQLite); batch prediction, SVM training, the enhanced/AutoML path, and the /docs, /predict/sample-model, /auth/login links all fail at runtime.

## Stack
Frontend: Next.js 15.3.5 (App Router, standalone output), React 19, TypeScript 5 (strict but ignored at build), Tailwind v4, framer-motion, axios, sonner. Backend: FastAPI 0.104, SQLAlchemy 2.0 (SQLite default / optional Postgres), JWT via python-jose + bcrypt/passlib, pandas/numpy/scikit-learn/XGBoost, joblib model persistence, OpenRouter/DeepSeek LLM (requests). Infra: multi-stage Docker for both services, docker-compose with healthchecks + optional redis/postgres profiles. No CI, no migrations wired.

## Roadmap

### P0 — Fixes (make it correct & runnable)
- [ ] **(S)** Fix POST /predict/batch crash
  - _why:_ predict.py:185 calls make_predictions(request) without the required current_user arg → TypeError; the advertised Batch Prediction tab fails at runtime. Refactor shared predict logic into a service function and call it from both single and batch handlers (passing current_user explicitly).
- [ ] **(M)** Enforce per-resource ownership (close IDOR)
  - _why:_ POST /predict/, all /summary/* and /predict/model/{id}/info load any model_id from disk with no user check, so any logged-in user can predict against and read others' models; GET /predict/models and GET /upload/session/{id}/info have no auth at all. Add a dependency that resolves model/session by (id, current_user.id) from ModelMetadata/FileMetadata and 404s otherwise; add auth to the two open endpoints (or point /models at the user-scoped /history/models).
- [ ] **(M)** Remove fake/hardcoded data from the UI
  - _why:_ Homepage renders hardcoded 'Recent Activity' (94.2% accuracy) for all users including logged-out, and the predict page hardcodes model accuracy to 0.95. Fabricated metrics destroy reviewer trust in every real number. Replace with real fetches from /history/files + /history/models behind auth (with a true empty state) and show the model's actual stored accuracy.
- [ ] **(S)** Fix dead navigation links
  - _why:_ Homepage links to /docs and /predict/sample-model (both 404/error) and the predict page redirects to /auth/login in 3 places (real route is /login), so the login redirect itself dead-ends on 404. First-impression demo-path breakages. Repoint to /login, build a real /docs page or hide the link, and wire 'Try Sample Model' to a real seeded model or remove it.
- [ ] **(M)** Reconcile training UI with backend algorithm contract
  - _why:_ The train UI offers SVM but POST /train/ hard-rejects anything outside [random_forest, logistic_regression, xgboost] with 400, and the enhanced path silently maps svm/naive_bayes/decision_tree onto other models. Either implement the offered algorithms in ml_processor.model_configs or remove them from the UI/recommender so selection is truthful.
- [ ] **(M)** De-duplicate the enhanced-train route and fix its crash
  - _why:_ /{session_id}/enhanced-train is declared twice (train.py:257 and :643) so the smart-selection handler is permanently unreachable, and ml_processor.train_model's preprocessed-input branch references an undefined `preprocessor` (NameError). Delete the duplicate, pick one canonical enhanced path, and fix the branch so it builds/passes a valid pipeline. Until fixed, the marketed AutoML never runs.
- [ ] **(S)** Fix database.py SQLAlchemy 2.0 break + DB-write swallowing
  - _why:_ database.py:31 runs raw conn.execute("SELECT 1") which throws under SQLAlchemy 2.0, so Postgres always falls back to SQLite even when configured; wrap with text(). Also upload/train swallow DB-save failures and return success, producing orphaned files/models that break ownership and history — make these failures hard errors.
- [ ] **(M)** Remove committed secrets and PII from repo + history
  - _why:_ data/othor_ai.db (a real email + bcrypt hash) is committed and docker-compose hardcodes SECRET_KEY and POSTGRES_PASSWORD; anyone with the repo can forge JWTs. git rm --cached the DB, add data/*.db to .gitignore, purge it from history (BFG/filter-repo), move all secrets to untracked env, and make SECRET_KEY a required var that fails startup on the placeholder.
- [ ] **(S)** Fix the two silent data bugs
  - _why:_ train.py:196 reads training_info['train_samples'] but ml_processor emits 'training_samples', so num_training_samples is always NULL in the DB; and the duplicate getModelSummary in lib/api.ts (lines 334 & 358) is a suppressed TS error. Both are quick correctness fixes.

### P1 — Features (reach the full product)
- [ ] **(S)** Wire SmartAnalysis to the real intelligent-analysis endpoint
  - _why:_ SmartAnalysis.tsx builds a hardcoded mockAnalysis with a 'endpoint doesn't exist yet' TODO, but GET /profile/{session}/intelligent-analysis already exists and api.ts already wraps it. A shipped feature shows fake data; connect it (or delete the component).
- [ ] **(L)** Make AutoML real: invoke hyperparameter tuning + CV model comparison
  - _why:_ smart_model_selector.optimize_hyperparameters (GridSearch/RandomizedSearch) and compare_models are fully written but never called by any endpoint, so 'AutoML' always uses fixed default hyperparameters. Wire them into the canonical enhanced-train path so tuned, CV-compared models are actually produced — this is what makes the product more than fixed-config training.
- [ ] **(L)** Rewrite enhanced preprocessing transformers as valid sklearn estimators
  - _why:_ enhanced_preprocessor custom transformers don't subclass BaseEstimator/TransformerMixin and the categorical pipeline can hand LabelEncoder a 2D matrix, so the enhanced ColumnTransformer breaks. Make them proper estimators with fit/transform/get_feature_names_out and add an end-to-end fit test, otherwise enhanced preprocessing cannot ship.
- [ ] **(L)** Move training to a background worker with job status
  - _why:_ Training runs synchronously in the request handler (blocks the event loop) while config allows 50MB / 1M rows and the frontend times out at 30s, so any real dataset fails. Use the Redis already in docker-compose (ARQ/Celery/RQ), return 202 + job id, persist status on ModelMetadata (the column exists), and add polling so progress bars reflect reality instead of cosmetic setTimeout steps.
- [ ] **(M)** Harden the LLM layer (async, retries, caching, grounding)
  - _why:_ llm_service uses sync requests.post inside async handlers (blocks up to 30s; /summary fires 3 sequential calls ≈90s), with no retries/caching/cost cap and fragile json.loads. Move to async httpx (or threadpool), add backoff + caching keyed on a stats hash, structured/JSON output with a validated schema, and a groundedness check that every number in the summary appears in the input stats. Also fix the backend↔frontend key mismatch (insights/business_applications vs key_findings/business_insights) so summaries actually render.
- [ ] **(L)** Real test suite + CI quality gate
  - _why:_ The pytest suite is stale (pre-auth, will 401) and there are zero frontend tests; next.config suppresses TS+ESLint so the green build is meaningless and there is no CI. Rewrite backend tests with an authenticated TestClient + temp DB (cover auth, IDOR, train→predict round-trip), add a few frontend tests, re-enable type/lint checks, and add a GitHub Actions workflow running pytest, tsc --noEmit, next lint+build, and docker build.
- [ ] **(M)** Auth/session UX: return-to-destination, refresh, expiry handling
  - _why:_ useAuthRedirect always pushes /login and discards the intended path, login always lands on /, the access token is 30 min with no refresh, and expiry silently bounces users via a hard window.location redirect losing their work. Persist the target path and redirect back after login, add a refresh token (or graceful 'session expired' toast), and wrap profile/train/enhanced/summary in ProtectedRoute so all authed pages guard consistently.
- [ ] **(M)** Unify the two training journeys and the two model lists
  - _why:_ train/[session] and train/[session]/enhanced share ~80% code (≈1,686 lines) with no story for when to use which, and 'Models' (global filesystem) vs 'History → models' (user-scoped DB) are two divergent lists. Extract a shared TrainingFlow/TrainingResults component with a basic/advanced toggle and converge on one user-scoped 'My Models' concept.
- [ ] **(M)** Replace fabricated regression confidence
  - _why:_ _calculate_confidence_scores invents regression 'confidence' as 1/(1+std) clamped to [0.1,0.9] — statistically meaningless and misleading. Use real prediction intervals (e.g. conformal/MAPIE) or remove the field; document classification confidence as max class probability.

### P2 — Polish & cleanup
- [ ] **(S)** Delete dead code and committed cruft
  - _why:_ dump/ (800K: an entire old frontend + 16 ad-hoc test scripts + debug HTML), predict/[model]/page_backup.tsx, root test_model_endpoints.py, and backend root setup_*/check_*/test_* scripts are pure dead weight that confuses reviewers. Also remove the 3 never-imported viz components (~1,760 lines) and the invalid recharts/heroicon imports in the still-used ComprehensiveDataAnalysis.
- [ ] **(M)** Collapse documentation to one README + a small docs/ set
  - _why:_ 9 markdown files + a 221K .docx + transcript.md + duplicate assignment copies overlap heavily (4 files explain Docker startup, 5 explain local setup) and self-contradict. Keep one accurate README, plus docs/architecture.md, docs/api-docs.md, docs/deployment.md; delete the rest and trim 6 startup scripts to one per OS.
- [ ] **(S)** Strip marketing overclaims and align docs with reality
  - _why:_ README claims refresh tokens, Celery, 'thousands of users', <100ms inference, 1M-sample scale, WCAG compliance, virus scanning, and documents tests/sample files that don't exist. The gap is itself a red flag in review. Cut to what's implemented and move the rest to a clearly labeled 'Future Work'.
- [ ] **(M)** Prune unused dependencies and unify the design system
  - _why:_ ~8 heavy unused deps ship (react-query, zustand, d3, react-hook-form, zod, most Radix packages) and two icon libraries run in parallel; the predict page renders its own duplicate nav + background. Either adopt react-hook-form+zod for forms or remove them, standardize on heroicons, use the existing Button variants, and remove the duplicate chrome.
- [ ] **(M)** Unify file-path resolution and config
  - _why:_ ml_processor, predict, summary, analysis hardcode relative Path('data/...') so behavior is CWD-dependent and ignores the UPLOAD_DIR/MODEL_DIR env vars docker-compose sets. Route all IO through settings.UPLOAD_DIR/MODEL_DIR (absolute), centralize SECRET_KEY/CORS/token-TTL in config, and honor ALLOWED_ORIGINS.
- [ ] **(M)** Modernize framework usage and add empty/loading states
  - _why:_ main.py uses deprecated @app.on_event and datetime.utcnow, schemas use pydantic v1 Config under v2, layout.tsx uses deprecated metadata.viewport. Migrate to lifespan and the Next 15 viewport export, and add genuine first-run empty states + the existing-but-unused Skeleton loaders instead of full-screen spinners.
- [ ] **(S)** Accessibility, logging, and console cleanup
  - _why:_ sr-only radio inputs lack focus rings, icon-only buttons/sliders lack aria-labels, status is color-only, and ~7 console.log/debug statements plus per-request axios logging remain. Add aria labels, focus-visible states, text alongside color, and gate logging behind a dev flag.

### Deployment
- [ ] **(S)** Fix environment-correct frontend build (NEXT_PUBLIC_API_URL)
  - _why:_ NEXT_PUBLIC_API_URL is inlined into the client bundle at build time and baked to localhost:8001, so a deployed frontend calls the user's own localhost and breaks. Make it a Dockerfile build-arg set per environment to the public backend URL, and add frontend/.env.example.
- [ ] **(M)** Production-grade backend serving and container hardening
  - _why:_ Backend runs a single bare uvicorn (no workers, won't use multiple cores), the container runs as root, there are no .dockerignore files (build context ships venvs/data/secrets), and the base image is python:3.9. Serve with gunicorn -k uvicorn workers, drop to a non-root user, add .dockerignore everywhere, bump to python:3.11-slim.
- [ ] **(L)** Managed Postgres + object storage instead of local bind mounts
  - _why:_ Uploads, models, and the SQLite DB live on the container filesystem and won't survive deploys; Postgres is currently broken (SELECT 1 bug). After fixing the DB, add alembic config + an initial migration (run on deploy instead of create_tables()), move to managed Postgres (Neon/Supabase/RDS) and S3-compatible storage for uploads/models.
- [ ] **(M)** Ship to a real platform with env-driven config
  - _why:_ Target frontend on Vercel (native Next.js) or a container platform, backend on Fly.io/Render/Railway or ECS Fargate, with all secrets (SECRET_KEY, DB creds, OPENROUTER_API_KEY) from a secret store and NEXT_PUBLIC_API_URL pointed at the public backend. Wire OPENROUTER_API_KEY through compose/env (currently not passed to the backend container, so LLM silently runs in fallback under Docker). For a single-box demo, a hardened docker-compose on a small VM with a real .env and external volumes is acceptable.
- [ ] **(M)** CI/CD pipeline
  - _why:_ There is zero automation. Add a GitHub Actions pipeline: backend pytest, frontend tsc --noEmit + lint + build, and docker build of both images (push to a registry on main), so quality and releases stop being entirely manual.

## Key decisions
- AutoML: commit or cut. Either invest the L effort to make smart selection + hyperparameter tuning + enhanced preprocessing real and reachable, OR delete the enhanced/intelligent/smart_model_selector modules and market only honest fixed-config training. Shipping broken AutoML is worse than not claiming it.
- Two training screens → one. Merge basic and enhanced into a single flow with an advanced toggle to kill ~1,686 duplicated lines and the 'which do I use' confusion.
- Model identity is the DB, not the filesystem. Make ModelMetadata (user-scoped) the single source of truth for ownership and listing; retire or auth+scope the filesystem-scanning /predict/models so there is one 'My Models' concept.
- Demo-readiness first, production second. Land all P0 (correctness, IDOR, secrets, dead links, fake data) before any P1 features — these are what a reviewer hits in the first five minutes and what makes the security story credible.
- Re-enable quality gates early. Turn TS+ESLint back on and stand up CI before large refactors so regressions are caught, accepting a one-time cleanup of currently-hidden errors.
- Storage strategy for deploy: move uploads/models/DB off the container filesystem (managed Postgres + S3) rather than persisting bind mounts, since the local-path coupling is already a source of CWD-dependent bugs.

## Risks
- Security is the most serious gap and it is live, not theoretical: IDOR on predict/summary (verified — no ownership check in handler bodies), two fully unauthenticated endpoints, and a committed DB with a real email + bcrypt hash plus hardcoded JWT signing key. Treat the secret as compromised: rotate SECRET_KEY and purge the DB from git history before any public push.
- The marketed 'AutoML/intelligent' layer is largely non-functional (dead duplicate route + NameError + sklearn-incompatible transformers + tuning never invoked). P1 here is genuinely L effort; if scope is tight, the honest move is to delete the enhanced layer and market only fixed-config training rather than ship broken AutoML.
- Quality gates are disabled (next.config ignores TS+ESLint) and the pytest suite is stale, so the 'green build' is misleading and current automated coverage is effectively zero. Re-enabling checks will surface a backlog of currently-hidden type/lint errors — budget for that before counting CI as 'done'.
- Synchronous in-request training will fail on any realistic dataset (50MB/1M-row limits vs a 30s frontend timeout). Demos work only because sample CSVs are tiny; do not advertise scale until the background worker (P1) lands.
- Postgres is silently broken (SELECT 1 under SQLAlchemy 2.0), so anyone who 'switches to the production DB' actually keeps running SQLite. Combined with no migrations, schema changes are unsafe — fix the DB bug and add alembic before claiming a production DB path.
- NEXT_PUBLIC_API_URL is baked at build time to localhost, so the frontend will appear deployed but call the wrong backend — a classic silent prod failure that won't show in local Docker testing.
- Honesty risk: the README overclaims (refresh tokens, Celery, thousands of users, <100ms, WCAG, virus scanning, non-existent tests/samples). For a take-home, the credibility cost of unsubstantiated claims is high; trimming docs to reality (P2) is low-effort and high-leverage.

## Estimated scope
Roughly a 4-6 week effort for one focused engineer to reach full form, sequenced in four waves. Wave 1 (P0, ~3-5 days): a tight demo-readiness + security sprint — fix batch/SVM/dead-links/fake-data, enforce ownership, fix the SELECT 1 and key bugs, purge secrets/PII, de-dupe the enhanced route. This alone makes it an honest, secure, demoable build. Wave 2 (P1 correctness, ~1 week): wire SmartAnalysis, async background training, harden+contract-fix the LLM layer, rewrite tests + add CI. Wave 3 (P1 depth, ~1-1.5 weeks): real AutoML (tuning/CV) and sklearn-correct enhanced preprocessing — or cut them — plus auth/session UX and the unified training flow. Wave 4 (P2 + deploy, ~3-5 days): repo/doc cleanup, dependency pruning, container hardening, env-driven config, managed Postgres + object storage, and ship via CI to Vercel + a container platform. If time-boxed, Wave 1 + the test/CI and cleanup slices deliver the highest credibility per hour.

## Cross-cutting standards (shared across all 3 repos)
- Auth/authorization as one shared pattern: all three route identity unsafely (Othor IDOR + 2 unauthenticated endpoints; Archer derives userId from query/body on 40 of 44 routes with a guard imported by zero routes and no root middleware; CryptAI has none yet). Standardize on JWT-in-httpOnly-cookie + a single server-side guard + an ownership/resource-scoping dependency, build it once in Othor, and port it.
- Secrets hygiene: hardcoded/default signing keys and committed credentials are universal — Othor commits a SQLite DB with a real email+bcrypt hash and hardcodes SECRET_KEY/POSTGRES_PASSWORD; Archer defaults JWT_SECRET to 'your-secret-key' in two auth systems; CryptAI ships realistic sk-... placeholders and weak compose passwords. Standard: fail-fast on missing/placeholder secrets at boot, rotate everything treated as compromised, purge secrets/PII from git history, and adopt a secret store for deploy.
- AI API keys must be server-only: Othor and Archer both inline billable LLM keys into the client bundle via NEXT_PUBLIC_* (Archer's Gemini key is server-side only by accident). Standardize on server-only env names and rotate.
- Env-driven config / no baked localhost: every repo hardcodes URLs or CWD-relative paths (CryptAI's localhost:8000 in App.tsx, Othor's build-time-baked NEXT_PUBLIC_API_URL=localhost:8001 and Path('data/...'), Archer's path-alias/config sprawl). Standardize a single typed settings module per service plus build-arg/runtime injection of the public API URL.
- CI quality gate is absent everywhere and quality gates are actively suppressed in the two Next apps (Othor next.config ignores TS+ESLint; Archer ignoreBuildErrors/ignoreDuringBuilds true). Standardize one GitHub Actions template: typecheck + lint + tests + docker build, and re-enable the suppressed gates early (incrementally) so hidden errors surface before refactors.
- Honest docs / kill fabricated data: each app shows invented numbers or overclaims (Othor's hardcoded 94.2%/0.95 accuracy + README claims of Celery/refresh-tokens/scale that don't exist; Archer's hardcoded performanceTrend arrays and 'AI' that is Math.random; CryptAI's docs describing a finished platform that is 97% absent). Standard: replace mock data with real fetches or true empty states, and trim copy to an 'implemented vs planned' table.
- Deploy shape is convergent: two Next apps -> Vercel (or container) + managed Mongo/Postgres + object storage + cron for background work; CryptAI is the outlier (stateful, multi-DB, WebSocket, long-running loop -> container platform/VM, never serverless). Reuse one container-platform + managed-data + CI/CD playbook across all three.
- Background/async work + durable scheduling: synchronous-in-request heavy work and ephemeral in-memory state appear in two repos (Othor trains in the request handler past a 30s timeout; Archer's scheduler/cache/rate-limiter live in module-level memory wiped on cold start). Standardize a worker/queue + DB-or-Redis-backed scheduling triggered by real cron.
